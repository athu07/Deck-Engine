THE GOAL (never changes — for context)
------------------------------------
A tool where sales/tech fill in client context (client name,
industry, work type, deck phase, recipient) + optionally paste
a transcript, and the tool assembles a tailored PowerPoint by
picking slides from the master deck (and generating any missing
slides via template). Preview, then download.

I am new to development. Explain simply, one step at a time,
wait for my confirmation before moving on.

Design decision: CONTENT LIBRARY, not positional index.
Every slide = a standalone record (stable ID + text + tags).
Deck order does NOT matter. Slides are matched by content/tags.
The engine AUTO-TAGS slides (rules first, AI later for unclear ones).

Build order (one box fully working before the next):
  Box 0 — Explode deck into auto-tagged library        [DONE]
  Box 1 — Brain (matcher): context in -> slide_ids out [DONE, form-only/rules-only]
  Box 2 — Assembler: slide_ids -> new .pptx            [DONE]
  Box 3 — Form + web page the team uses                [DONE, runs locally]
  Box 4 — Deploy + v2 polish (transcript/AI, gap-fill,
          file-size cleanup, formatting, deploy)        <-- WE ARE HERE

Files in this folder:

  - Metadata registry (.xlsx) — reference for good tags + Selection Rules
  - This build log

WHAT WORKS (done & tested)
------------------------------------
Pipeline (all rules-only, no AI, no API cost):
  context -> matcher.py -> slide_ids -> assembler.py -> Tailored_Deck.pptx
  ...and a browser form (app.py) that does the whole thing + download.

Scripts:
  - stamp_ids.py     — stamps permanent J2W_ID into each slide's NOTES.
                       INSERT-SAFE: only un-ID'd slides get a new id
                       (max existing + 1); existing ids never renumber.
  - build_library.py — deck -> library.json (68 standalone records:
                       id + title/subtitle/text + pointer to slide).
  - tagger.py        — rule-based tags (kind/work_type/industry/function)
                       + per-tag confidence (AUTO/HUMAN) + keyword string.
                       vs registry: kind 88%, industry 67%, work_type 65%,
                       function 45%, keywords 100% captured.
  - ai_fallback.py   — OPTIONAL AI second opinion (OpenAI). Dry-run by
                       default; --apply to call the API. (See DECISIONS:
                       did NOT beat rules on this task — left in but unused.)
  - matcher.py       — Box 1 brain. Reads the registry's include_rule /
                       std_group / section to apply the Selection Rules.
                       Form-only for now (no transcript).
  - assembler.py     — Box 2. Keeps only chosen slides, in order, into a
                       NEW .pptx. Formatting preserved perfectly.
  - app.py           — Box 3. Flask form at http://127.0.0.1:5000 ->
                       preview -> download. Run with:  py app.py
  - secrets_loader.py + .env — API key kept out of code (.env is git-ignored).

Data files:
  - WORKING_COPY_Master_Deck.pptx — copy, all 68 slides ID-stamped.
  - library.json / tagged_library.json — the content library.
  - output/Tailored_Deck_*.pptx — generated decks.
Originals never modified (verified by byte-compare).

ADD LIBRARY SLIDES TO A DECK — "DECK TRAY" — DONE 23 June 2026
  Goal: from the Slide library, hand-pick any slide into the deck you're building.
  (NOTE: the Suggested-slides page already had an "Add slide" picker for all 133
  slides; this adds the same power from the nicer Library browse view.)
  HOW IT WORKS — a browser-side "deck tray" (localStorage key j2w_deck), no server
  session / no DB:
    - Library cards get a "+ Add to deck" button; a floating "Open deck (N)" pill
      shows the count and links to the deck. Cards already in the deck show a tick.
    - The deck tray stores {active, ctx{client/industry/phase/recipient/transcript/
      functions[]/work_types[]}, order[ids], buildId}.
    - Suggested-slides page (BUILD_BODY): on a NEW build it seeds the tray from the
      matcher picks + current form context (overwrites = fresh deck). Every reorder/
      add/remove persists the order back to the tray.
    - NEW route GET /deck re-opens the deck: rebuilds the slide list from the tray
      and refills the hidden form fields (client/phase/etc.) client-side, so
      Download/Review/Generate + meeting-logging all keep working unchanged.
    - buildId guard: re-opening the SAME build (e.g. browser Back) restores the deck
      as left (keeps library adds) instead of resetting to the matcher picks.
  UNCHANGED: matcher, assembler, meeting_log, /download, /review, /finalize — they
  still just receive the final slide-id list + context.
  LIMITATION (acceptable): if you start a deck COLD from the library (no build yet),
  there's no client name/phase context — /download then defaults client to "Client".
  Intended flow is build -> jump to library -> add -> Open deck. Manual adds also
  bypass matcher exclusions (you can deliberately add a divider/leader slide).
  Verified: routes /, /library, /deck, /meetings all 200; library renders add
  buttons + pill; /deck is in resume mode; /build renders with the tray vars.

7 July 2026 -- Reskin: background/text legibility rule (contrast-aware fix)
------------------------------------
Owner spotted a real bug in a screenshot: on the step-badge slide, the number
inside each red circle badge ("1".."6") was rendering in TEAL -- because
_restyle_box correctly colours the badge red, and separately the "subheadings
are always teal" rule (above) correctly colours a 15pt label teal, but neither
rule knew about the OTHER -- red bg + teal text is a genuinely illegible
pairing (WCAG contrast ratio ~1.5, checked -- see below). Owner's rule: red
vs teal/green, either direction, is not legible; red+white and green+white
both read fine.
Added as real, reusable metadata alongside the palette constants (TEAL, RED,
etc. -- not a one-off patch): _MIN_CONTRAST + a genuine WCAG-style relative-
luminance contrast-ratio calculation (gamma-corrected sRGB), plus a small
_NAMED_SAFE_TEXT override so red/teal boxes specifically always get WHITE text
(matches the owner's literal rule, even though for teal ink scores a hair
higher on raw contrast math). New _fix_text_on_box_contrast() runs as a second
pass per slide, AFTER box fills and role colours are both already set: for
every text shape, find which coloured box it visually sits on top of (by
rect overlap) and, if the current text colour reads under _MIN_CONTRAST
against that box, flip it to a legible one.
Two real bugs found and fixed along the way (not hypothetical -- caught by
testing against the actual ExpenseIQ deck):
  1. A text shape can overlap MULTIPLE boxes at once (e.g. a small badge
     nested inside a larger card behind it). The first version matched
     whichever box came first in document order and got the outer CARD_BG
     grey instead of the badge red sitting directly underneath -- contrast
     against grey read as fine, so nothing got fixed. Now picks the
     SMALLEST-area overlapping box (the immediately-underlying shape).
  2. The same general contrast check also caught an unrelated pre-existing
     issue: a pill/banner box recoloured to our light CARD_BG still had its
     ORIGINAL white text (authored for whatever colour the box used to be),
     which is a WCAG ratio of ~1.1 against F5F5F5 -- effectively invisible.
     That's now flipped to ink automatically, same mechanism, no special case
     needed -- confirms the general contrast-ratio approach (vs. a fixed
     lookup table) is the right shape for this rule, since it also caught a
     bug the owner didn't report or screenshot.

8 July 2026 -- Reskin: body-text sizing + a REAL computed shrink-to-fit
------------------------------------
Owner flagged another real bug via screenshot (a GSK deck's "Next Steps"
slide, three cards each with a bold mini-heading + a description paragraph +
a "FOR YOUR CONFIRMATION" label + a checklist): text was visibly overlapping.
Root cause, traced against the actual source file (J2W_GSK_RegIQ_Framework.
pptx, slide 9): every one of those pieces -- a 12pt bold mini-heading, an
8.5pt paragraph, a 7pt caption label, 8.5pt checklist items -- was being
flattened to one uniform SZ_BODY (13pt) by the old "body" role handling. The
smaller-original pieces got blown up the most (7pt -> 13pt is +86%), and
their boxes were tightly authored around their SMALL original sizes (e.g. a
0.20in-tall box for a 7pt caption), so they overflowed into the shape below.
Two-part fix in reskin.py:
  1. Owner's new spec: SZ_BODY 13 -> 11 (plain content), new SZ_BODY_HEAD = 13
     (a card's own bold mini-heading, nested inside body -- NOT the page-level
     Oswald heading). Which is which is decided per RUN, not per shape: a bold
     run whose ORIGINAL size was already >= 10pt (SZ_BODY_HEAD_MIN_ORIG)
     becomes a mini-heading at 13; everything else -- including a tiny BOLD
     caption like "FOR YOUR CONFIRMATION" at 7pt originally -- stays content
     at 11. Without that size floor, tiny bold labels would also jump to 13
     in boxes sized for ~7pt text, recreating the same overflow one size class
     down.
  2. Even 11pt still doesn't fit every box -- checked the actual numbers: the
     GSK deck's longest body paragraph (241 characters) needs an estimated
     ~1.65in at 11pt but its box is only 1.00in tall. `auto_size =
     TEXT_TO_FIT_SHAPE` (already set) only marks a shape as "should shrink" --
     python-pptx does not compute the actual shrink, and testing confirms real
     renderers don't reliably (re)compute it live either, which is exactly why
     the owner saw literal-size overflow in the first place. New
     _fit_body_text() genuinely estimates wrapped line count (character count
     vs. box width, ~PowerPoint's own autofit heuristic) and, if that's taller
     than the box, bakes a REAL fontScale into the XML (<a:normAutofit
     fontScale=... lnSpcReduction=.../>) -- floor 60% of the set size, so a
     hopelessly undersized box still shrinks-and-reads rather than vanishing.
     This makes the shrink part of the saved file itself, not a hope that
     whatever opens it recalculates it.
VERIFIED against the real GSK deck: "Share an open innovation challenge"
(originally 12pt bold) -> 13pt, ~91% fontScale (barely shrunk, fits almost
exactly as before); "NEXT STEP"/"FOR YOUR CONFIRMATION" (originally 7-7.5pt
bold) -> 11pt then shrunk further (64%/60%) since their boxes are tiny;
checklist items -> 11pt, ~75% scale; the long body paragraph -> 11pt, hits
the 60% floor (the box was always going to need real help). Re-verified the
ExpenseIQ deck too (previous fixes) -- no regressions, badge numbers still
white-on-red, card mini-headings ("Employee", "AI agent"...) correctly
promoted to 13pt. Zip integrity clean on both, 16/16 pytest green.

8 July 2026 -- Crash: "Create deck" (/build) throwing Internal Server Error
------------------------------------
Owner reported /build 500ing on a real click. Read the server's own error
log (not a guess) -- exact traceback:
  matcher.py:534 in plan() -> _case_reason(wt, {**it, "research": True})
  matcher.py:83 in _case_reason() -> f"...({item['score']:.1f})"
  KeyError: 'score'
Root cause: matcher.plan()'s priority_ids loop has a fallback branch for a
priority pick that matched a named case ID but didn't appear in the overall
relevance ranking ("matched a hook but ranked low") -- it builds a
substitute item dict by hand, and that hand-built dict was MISSING the
"score" key that _case_reason() unconditionally reads at the very end of the
line. Any priority id landing in that specific fallback crashed the whole
build with no graceful degradation.
This fallback branch existed before today, but the STRATEGIC BET feature
added earlier today (see entry above) makes it far more likely to trigger:
bet-selected cases come from relevance.shortlist_cases() -- a different,
semantic-shortlist selection path than the main relevance.rank_cases() that
populates ranked_by_id -- so a bet-selected case landing in this "ranked low
or filtered out" fallback is now a realistic, not just theoretical, path.
Fixed two ways (defence in depth, not just patching the one call site):
  1. matcher.py's fallback dict now includes "score": 0.0 -- honest, not a
     guess: this case genuinely has no ranked score, that's WHY it's in the
     fallback branch in the first place.
  2. _case_reason() itself changed from item['score'] to item.get('score',
     0.0) -- a one-line, zero-risk defensive fix that closes this entire bug
     CLASS for any other caller that might ever hand it an incomplete dict,
     not just this one.
VERIFIED: reproduced the EXACT crashing dict directly against _case_reason()
pre-fix (confirmed it throws the identical KeyError), then confirmed the
post-fix version returns cleanly. Re-ran the real /build POST that
originally surfaced this (Waaree Group / Pankaj Kumar Pant, the same
strategic-bet scenario from earlier today) through the actual Flask app --
200, rationale panel renders, no crash. Full pytest green.

BUG: six of nine slide-saves 404'd on records that existed. A TORN READ.
Athithia's console showed POST /builder/slide/G120 -> 404 (and G117, G121-
G124), while G116/G118/G119 returned 200. staging.json contained all of them.

Root cause: staging._save() was

which TRUNCATES the file and then streams ~124 records into it. Writes were
serialised by _ADD_LOCK (added earlier today), but READS were not, and

the truncate-to-complete window gets a JSON syntax error; _load() swallows
every exception and returns [], so get() returns None and the route aborts
404 on a record sitting in the file the whole time. The Custom Slide Builder
POSTs every card at once when you download, so most of them lost the race.

    truncating write -> 207/300 reads saw nothing
    atomic write     ->   0/300

one os.replace() over the top (atomic on POSIX and Windows). A reader sees the
old complete file or the new complete file, never a torn one -- no read lock
needed. Applied to every store a request can read while another writes:
staging.json, library.json, tagged_library.json, the content store, the case
embeddings, and custom_industries.json. Also put mark_promoted(),
update_content() and _set_status() -- all read-modify-writes -- under the same
